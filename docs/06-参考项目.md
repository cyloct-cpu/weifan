# 参考项目调研

> 调研时间 2026-10-29。以下信息来自各仓库的 README / 检索摘要，**未逐一 clone 核对**。
> 使用前请自己确认三件事：License、最近一次提交时间、是否还在维护。

## 0. 结论先行

有三类项目值得看，各自的用途完全不同：

| 类别 | 用途 | 代表项目 |
|---|---|---|
| iOS 键盘脚手架 | **省掉我们 `KeyboardViewController` 那 340 行 UI 代码** | KeyboardKit、giellakbd-ios、azooKey |
| 安卓无障碍改写 | **验证 D-13 的安卓方案，直接抄实现细节** | SwiftSlate、JevChat-Jarvis、TypeAssist |
| WhatsApp 网页扩展 | **验证"浏览器扩展优先"这个判断；DOM 选择器可直接抄** | wa-translator、Transify、WordWave |

---

## 1. iOS：键盘脚手架

### 1.1 KeyboardKit（最值得先看）

- 仓库：`github.com/KeyboardKit/KeyboardKit`（作者 Daniel Saidi）
- 语言：Swift / SwiftUI，SPM 引入
- 定位：**不是翻译工具，而是"做键盘扩展的 SDK"**——把 Apple 那套极其难用的 `UIInputViewController` API 包装成可用的东西。

**能偷什么**：
- 我们手写的语言芯片、按钮条、状态条，在 KeyboardKit 里都是现成组件；
- 它扩展了 `UITextDocumentProxy`（读取上下文、删除整段、选区处理），正好覆盖我们 V-01 要验证的那部分；
- 自带"识别宿主 App"的能力（`Host`）——这可能**部分解决 V-06**（键盘不知道自己在跟谁聊）的问题，值得优先确认；
- 支持 68 个语种的本地化布局。

**注意**：
- 核心开源、Pro 功能收费（Pro 提供完整本地化布局与自动补全）。我们只用核心即可；
- 引入它等于多一层依赖，且它的抽象较重。如果只是想省 UI 代码，可以先看它的实现思路再自己写——我们的键盘只有 4 个按钮，未必值得引整个 SDK。

**对我们代码的映射**：`ios/Sources/Keyboard/KeyboardViewController.swift` 里的 `buildUI()` 与 `rebuildChips()` 是被它直接替代的部分；翻译调用逻辑（`TranslationCore`）保持不变。

### 1.2 giellakbd-ios

- 仓库：`github.com/nondescriptpointer/giellakbd-ios`（原属 divvun 组织）
- 定位：Apple 原生键盘的开源重实现，面向少数民族语言。
- 双 License：MIT / Apache-2.0，可商用。

**能偷什么**：一套**完整键盘的布局、按键命中、横竖屏适配**是怎么组织的。我们不做字母键盘，但"键盘扩展在不同设备上的高度与安全区处理"这块坑，它都趟过了。

**注意**：用 CocoaPods，构建链较老。

### 1.3 azooKey

- 仓库：`github.com/azooKey/azooKey`
- 定位：能在 App Store 上架的日语输入法，自带神经网络假名汉字转换引擎（Zenzai），SwiftUI 界面。
- License：MIT。

**能偷什么**：
- 它是"**在键盘扩展里塞一个模型**"的现成案例——正是我们在 D-11 里判断"iOS 键盘跑不动本地模型"时该拿来对照的样本。看完它的内存与启动表现，我们对"能不能本地转写语音/本地翻译"的判断会更硬。
- 三 target（主 App / 键盘 / 共享核心 `AzooKeyCore`）的结构和我们完全同构，可以对照它如何切分模块。

**注意**：它证明了"要自己实现输入法"是多大的工程——**这正是 D-02 拒绝自研拼音输入法的依据**。

## 2. 安卓：无障碍改写（这条路已被验证）

### 2.1 SwiftSlate ⭐ 最贴近我们的方案

- 仓库：`github.com/Musheer360/SwiftSlate`
- 语言：Kotlin，MIT，已上 F-Droid
- 定位：在任何 App 里输入文字后，末尾加一个触发后缀（如 `?translate:es`、`?fix`、`?formal`），通过无障碍服务**原地替换**成结果。

**为什么重要**：它的核心机制和我们在 `docs/03-四端路线图.md` 里给安卓设计的"悬浮球 + `ACTION_SET_TEXT`"**是同一件事**，而它已经跑通并上架了。可以直接抄：

- 用 `AccessibilityNodeInfo.ACTION_SET_TEXT` 写回输入框的具体写法；
- 哪些 App 的自绘输入框不吃这一套（README 明确说"部分自定义输入框不支持"）；
- 加密存 key（AES-256-GCM + Android Keystore）的做法，对应我们的 Keychain；
- 支持 OpenAI 兼容端点，含 Ollama / LM Studio 本地推理——**这给 D-10"直连云 API"提供了另一条路：不想让聊天内容出网的人可以指向本机模型**。

**它比我们的设计更好的地方**：**用触发后缀代替悬浮球**。打「这批货下周能发吗？?译」然后原地变西语——不需要点任何按钮、不需要悬浮窗权限。这个交互值得抄进安卓版，甚至可以考虑"后缀触发"作为主交互、悬浮球作为备选。

### 2.2 JevChat-Jarvis

- 仓库：`jev-chat/jev-chat-jarvis`
- 语言：Kotlin，MIT，2026 年 9 月发布，短时间 5000+ star
- 定位：安卓聊天副驾，读当前会话 → 生成候选回复 → **填入输入框，从不自动发送**。另有 macOS 与 Windows 配套版本。

**为什么重要**：它的三条设计原则和我们**一模一样**，等于给 D-01 做了背书：
1. 只读无障碍节点，不 hook、不改包、不调私有 API（降低封号风险）；
2. **只填草稿，发送权永远在人**；
3. 明确排除转账/收款等金流场景。

它的 README 还直说 iOS 因沙盒限制不支持——与我们在 D-02 的判断一致。

**能偷什么**：跨 App 读取聊天上下文的解析策略（不同 App 的节点树差异怎么归一化）；它只有 120–180ms 的屏幕解析延迟，值得对照我们的性能预算。

### 2.3 TypeAssist

- 仓库：`estiaksoyeb/TypeAssist`
- 与 SwiftSlate 同类，额外提供离线工具（计算、片段展开、密码生成）作为"不调模型也能干活"的部分。

**能偷什么**：**离线/在线功能分层的思路**——把不花钱、不会失败的功能（术语替换、片段插入）和要花钱、会失败的功能（翻译）分开，是降低"每次都要等网络"挫败感的好办法。对应到我们：`keepOriginal` 黑名单其实可以纯本地先跑一遍。

## 3. WhatsApp 网页扩展：这条路已经有人走完了

### 3.1 wa-translator

- 仓库：`github.com/slashslashbv/wa-translator`
- 定位：Chrome 扩展，WhatsApp Web 消息翻译（GPT-3.5），收发双向，带 63 个单元测试。

**能偷什么**：
- **DOM 注入与监听的完整实现**：`MutationObserver` 观察新消息、在气泡旁插入 🌐 按钮、译文显示在原文下方而不改动原文；
- 发件框的定位与写入方式；
- 它的作者明确写了"不确定是否完全符合 Chrome 的服务条款"，且**选择不上架商店、仅供本地运行**——和我们的 D-01 定位一样。

### 3.2 Transify ⭐ 踩过的坑最值钱

- 仓库：`github.com/Karam-999/transify-ai`（旧版 `Transify--An-extension-for-real-time-chat-translation`）
- 定位：一个扩展同时支持 WhatsApp Web / Telegram / Discord / Teams / Messenger / Instagram DM。

**它的两次迭代正好印证了我们的两个决策**：

| 它的经历 | 对应的我们的决策 |
|---|---|
| 早期用 MyMemory / LibreTranslate 免费 API，"I'm dead serious" 被译成跟死亡有关的句子，上下文全无 | **D-05 混合路由是对的**：纯机翻在长句和语气上确实不行 |
| 旧版在 API 失败时**静默返回原文当译文**，用户以为翻译了其实没有 | **我们的铁律"任何失败都不能静默"是对的**（`docs/02-技术方案.md` §8） |
| 后来换 Llama 3.3 70B via Groq，实测 <200ms | 大模型不一定慢，Groq 这类推理加速值得作为 D-05 的候选供应商 |
| 用 Next.js 后端代理，把 key 放服务端并解决 CORS | 与我们 D-10（直连）相反的选择。**扩展形态下 CORS 会逼你建中转**，这是浏览器扩展相对原生端的一个隐性成本 |

**能偷什么**：语气档位（Casual / Professional / Empathetic / Playful）的设计，可以直接映射到我们的 `TranslationStyle`；它的提示词工程值得对照我们的系统提示词改一版。

### 3.3 WordWave、paoloartasensi/WhatsAppWeb_ita_eng_extension

更小、更简单的实现，适合**第一次跑通 DOM 选择器**时对照：怎么找到消息气泡、怎么找到输入框、怎么在 WhatsApp 改版后快速修选择器。后者还用 MyMemory + LibreTranslate 做主备，是"零成本起步"的样本。

## 4. 离线引擎（如果将来想砍掉云依赖）

还没细查，但方向明确，记在这里备查：

| 项目 | 用途 | 对我们的意义 |
|---|---|---|
| LibreTranslate | 可自建的翻译 API，兼容 Google 风格接口 | 想自建中转（D-10 的反面）时的现成服务端 |
| Argos Translate | 离线的神经机器翻译模型（Python） | 桌面端（mac/win）本地翻译的候选；iOS 键盘跑不动 |
| whisper.cpp | Whisper 的 C/C++ 实现，可端上跑 | 语音转写本地化的唯一现实路径；但要评估键盘扩展 30–60MB 的内存上限 |
| Apple Translation framework | iOS 17.4+ 系统级端上翻译 | **免费 + 离线 + 无需密钥**，如果能在键盘扩展里调用，D-05 的成本模型直接改写。**必须先验证可用性与支持语种**，这是最值得优先试的一条 |

> Apple Translation framework 若可用，最划算的组合是：**短句走系统端上翻译（免费、零延迟、不出网），长句/含金额走大模型**。这比现在的"机翻 API + 大模型"更省，也更符合隐私取向。列入 `docs/04-待验证清单.md` 的验证队列。

## 5. 明确**不要**参考的方向

| 类型 | 例子 | 为什么不要 |
|---|---|---|
| WhatsApp 协议库 / 非官方客户端 | Baileys、open-wa、whatsapp-web.js | 它们靠逆向 WhatsApp Web 协议模拟登录，**封号风险极高**，且一旦协议变更全部失效。我们只做"人手动发"的辅助，不碰协议层 |
| 改包 / Hook / 注入 | Xposed 模块、越狱插件 | 违反服务条款，iOS 需越狱，安卓需 root 或改包签名 |
| "自动回复机器人" | 各种 auto-reply bot | 与 D-01 的合规底线冲突：**发送权必须留在人手上** |

## 6. 可直接抄的清单（按回报排序）

1. **安卓的"后缀触发"交互**（来自 SwiftSlate）——比悬浮球更轻，不需要悬浮窗权限。建议在安卓版替换掉 04 文档里的悬浮球方案。
2. **`ACTION_SET_TEXT` 的兼容性清单**（来自 SwiftSlate 的 README）——哪些 App 不支持，提前知道能省一周。
3. **Transify 的语气档位提示词**——补强我们的 `systemPrompt`。
4. **wa-translator 的 `MutationObserver` + 注入模式**——浏览器扩展版的骨架。
5. **KeyboardKit 的 `Host` 能力**——可能解决 V-06（键盘不知道当前会话对象）。
6. **azooKey 的键盘内存占用实测数据**——校准我们对"键盘里能跑多少东西"的直觉。

## 7. 一句话总结

我们的方向没有走错，但**没有一处需要从零发明**：

- iOS 的键盘架子：KeyboardKit 已经做好；
- 安卓的无障碍改写：SwiftSlate / Jev 已经跑通并上架；
- 网页扩展：至少四个项目在做同一件事，DOM 选择器和坑位都是公开的；
- 真正属于我们自己的、别人没做的，只有一件事：**"把这三条路统一到一套翻译判断逻辑上"**——也就是 `core/` 那 600 行。

所以下一步的正确顺序不变：先把 iOS 的 A-1~A-4 跑通，但在写任何新代码之前，**花两小时读一遍 SwiftSlate 和 wa-translator 的源码**，能省掉大量试错。
