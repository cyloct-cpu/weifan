## 一、目标与形态决策

### 1.1 目标

iOS 版做成 **WhatsApp 多设备客户端**（与 Android 版同定位、同能力），UI 与功能对齐 WATransChat iOS 2.82，
**排除**会员/付费/内购、AI 客服、VoIP 通话翻译、在线客服。

### 1.2 与现有 iOS 资产的关系（决策）

现在 `weifan/ios` 是一个**翻译工具**（App + 键盘扩展 + 分享扩展，1213 行）：
- 键盘扩展：在 WhatsApp 里把输入框中文替换成译文 ← 真机可用，模拟器验证不了（模拟器装不了 WhatsApp）
- 分享扩展：把外部内容分享进来翻译
- 主 App：试译 + 客户档案 + 术语表 + 设置

**决策：不废弃，做「双形态同一个 App」。**

| | 形态 A：翻译工具（现有） | 形态 B：多设备客户端（新增） |
|---|---|---|
| 入口 | 底部 tab「翻译」 | 底部 tab「会话」 |
| 依赖 | `WeiFanCore`（已有，27 测试通过） | `WeifanProtocol.xcframework`（待编） |
| 用途 | 没配对时也能用；在 WhatsApp 内靠键盘 | 直接收发 WhatsApp 消息 |
| 验证 | 模拟器可全验 | **模拟器可全验**（我们自己是客户端，只需手机 WhatsApp 扫码配对） |

理由：键盘扩展是 iOS 独有优势（Android 靠无障碍，iOS 只能靠键盘），不能因为做客户端就丢掉；
而两个形态共用翻译内核与本地设置，改造成本低。

**验证可行性说明**：模拟器装不了 WhatsApp，但**我们自己的 App 是客户端**，可以在模拟器里跑起来、
用手机上的 WhatsApp 扫码配对、然后完整收发消息——所以阶段 1–3 都能在模拟器验证。
只有"在 WhatsApp 内用键盘替换输入框"这一条必须真机。

## 二、技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| UI | SwiftUI（iOS 16+） | 与 WATransChat 一致；无 storyboard 更易维护 |
| 协议 | `gomobile bind -target=ios,iossimulator` → `WeifanProtocol.xcframework` | 复用现有 47 个 Go 方法，不重写协议 |
| 本地库 | **GRDB**（SQLite） | WATransChat 同款；比手写 SQLite 安全；支持迁移 |
| 图片加载 | 自研轻量异步加载 + 内存 LRU（或 Kingfisher） | 先自研，避免多一层依赖；若复杂再引 Kingfisher |
| 翻译 | 现有 `WeiFanCore` | 已 27 测试通过 |
| 依赖管理 | SwiftPM（`project.yml` 用 XcodeGen 生成工程） | 现有工程已如此 |

### 3.4 风险与预案

| 风险 | 预案 |
|---|---|
| gomobile 对新 Xcode 27 不兼容 | 降级用 `-target=ios` 只编真机，或改用 `c-archive` + 手写桥 |
| 模拟器架构不匹配（M 芯片需 arm64-sim） | 脚本已带 `iossimulator`；若失败单独编 `-target=iossimulator` 合并 |
| sqlite 驱动在 iOS 受限 | 现有 Go 层已用纯 Go 驱动（`modernc.org/sqlite`），无需 CGO |
| 包体积暴涨 | xcframework 双架构约 80–160MB；接受（微信级应用同量级） |

## 四、阶段 1：最小闭环（配对 + 列表 + 会话 + 本地库，预计 3–5 天）

### 4.1 本地数据库（对齐 Android `ChatDb` v9）

用 GRDB 建库，表结构与 Android 保持一致，便于两端逻辑互推：

```
chats(jid PK, title, last_message, last_ts, unread, pinned, archived, muted, blocked, note)
messages(chat_jid, id, sender_jid, from_me, text, original, translated, translated_lang, ts,
         media_kind, media_mime, media_name, media_size, media_path, media_thumb, media_meta,
         PK(chat_jid,id))
labels(id PK, name UNIQUE, color)
chat_labels(chat_jid, label_id, PK(chat_jid,label_id))
poll_votes(chat_jid, poll_msg_id, voter_jid, option_name, voter_name, ts, PK(…4列))
todos(id PK, chat_jid, content, due_ts, done, created_ts)   ← 阶段 3 再用
```

迁移策略：`DatabaseMigrator` 里按 v1…v9 顺序注册，与 Android 版本号对齐。

### 4.2 页面与任务

| 页面 | 任务 | 参考文案 key |

### 4.3 关键逻辑

1. **配对流程**：`PairWithQR` 回调出二维码字符串 → 渲染成图；`PairWithPhone(phone)` 等 8 位码输入
2. **消息监听**：`SetMessageListener` → 落库 → 更新会话列表 → 若在会话中则插入气泡
3. **发消息**：直译直发（中文 → 对方语言），原文存 `original`
4. **翻译**：复用 `WeiFanCore`，按对方国家推断目标语言
5. **连接状态**：`SetConnectionListener` → 顶部状态条

### 4.4 验收标准（必须真跑）

- [ ] 首次启动进语言选择 → 选中文 → 进配对页
- [ ] 手机 WhatsApp 扫码 → 模拟器内配对成功，会话列表出现历史会话
- [ ] 点开会话 → 消息正常渲染（含翻译行）
- [ ] 发一条中文 → 对方收到译文 → 回执变蓝
- [ ] 冷启动后数据仍在（GRDB 落盘）
- [ ] XCUITest：四页可达 + 配对页元素存在

## 十、前置依赖：等 Android 补齐 B1–B6

iOS 阶段 3 的多项能力（汇率、备份恢复、设备管理、译文字号、历史消息独立引擎、换引擎重译）
在 Android 端**尚未实现**。按用户要求，**先在 Android 落地并实测**，再平移到 iOS——
好处：iOS 只做 UI，业务规则与边界条件已在 Android 验证过，避免两端各写一版各踩一次坑。

Android 补齐顺序（见 docs/15 §6 与 docs/14 §8.2）：
1. **B1 汇率转换**（收益最高：报价场景直接算）
2. **B6 换引擎重译**（接口挂掉能立刻换）
3. **B4 译文字号**（小改动，顺手）
4. **B5 历史消息独立引擎**（小改动）
5. **B2 备份与恢复**（工作量大，价值高）
6. **B3 多设备管理**（依赖服务端是否支持，需先探测）
