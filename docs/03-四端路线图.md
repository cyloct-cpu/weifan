# 四端路线图

四端的技术路径**完全不同**，能复用的只有 `core` 那层的判断逻辑（D-12）。下面按建议顺序排列，每一端都写清"靠什么能力、卡在哪、什么时候该放弃某条路"。

---

## 1. Android（第二端，建议）

### 能力盘点

| 能力 | API | 能做什么 |
|---|---|---|
| 无障碍服务 | `AccessibilityService` | 读屏幕上任意 App 的文本节点、模拟点击、**直接改写输入框**（`ACTION_SET_TEXT`） |
| 通知监听 | `NotificationListenerService` | 读 WhatsApp 通知里的消息文本，可发译文通知 |
| 自定义输入法 | `InputMethodService` | 完全接管键盘，但同样要自己实现中文输入 |
| 悬浮窗 | `SYSTEM_ALERT_WINDOW` | 常驻小气泡按钮 |

### 推荐路径：悬浮气泡 + 无障碍改写（不做输入法）

```
点悬浮气泡 → 通过无障碍读当前输入框文本 → 翻译 → ACTION_SET_TEXT 写回
```

**为什么这比 iOS 体验好一个量级**：安卓可以在**不切换键盘**的情况下直接改写输入框，用户打完中文点一下气泡就完成，不需要切键盘、不需要切回来。这是安卓相对 iOS 的核心优势，务必用上。

**做输入法反而是下策**：`InputMethodService` 一接管键盘，用户就打不了中文（同 iOS 的困境），而且用户换输入法的心理成本很高。

### 卡点（按痛苦程度排序）

1. **无障碍被系统杀**：MIUI / EMUI / ColorOS 会在息屏后杀掉无障碍服务。必须做引导页：电池优化白名单、自启动、后台弹窗权限、锁定后台。
2. **`ACTION_SET_TEXT` 不一定生效**：部分 App 的自绘输入框不接受。需要回退到"粘贴板 + 模拟长按粘贴"。
3. **读通知拿消息**：`NotificationListenerService` 能拿到消息文本，但同一会话多条消息会被折叠，且无法区分自己发的和对方发的（要结合通知的 `EXTRA_MESSAGES`）。
4. **Google Play 政策**：无障碍 API 用于非无障碍目的会被拒。自用侧载无所谓，上架要改走输入法或 Share Target。

### 复用点

- `core` 全部逻辑用 Kotlin 重写（约 600–800 行）；
- `Scripts/main.swift` 里的断言集当作跨语言一致性基准；
- 提示词、路由阈值、风险原因定义照抄。

## 2. Windows（第三端）

### 能力盘点

| 能力 | API | 可靠性 |
|---|---|---|
| 剪贴板 + 全局热键 | `RegisterHotKey` + `Clipboard` | 高 |
| UI Automation | `UIAutomationClient` | 中，随 App 改版易碎 |
| 输入注入 | `SendInput` | 高 |

### 推荐路径：剪贴板热键 + 悬浮结果窗

```
选中文本（或全选输入框）→ Ctrl+C → Alt+T → 弹出译文窗 → Enter 复制译文 → Ctrl+V
```

**为什么不用 UI Automation 作为第一版**：WhatsApp Desktop 是 WinUI 打包应用，UIA 树结构不透明且随版本变化；一次改版就可能全废。剪贴板方案对任何 App 都成立，且实现只要几百行。

**进阶**：在剪贴板方案稳定后，再用 UIA 做"读最近一条对方消息"（用于语言检测），失败就退回手动选语言。

### 卡点

- 全局热键冲突（Alt+T 常被占用，需可配置）；
- 剪贴板被其他工具（如输入法、剪贴板管理器）抢占；
- 要处理"复制到剪贴板"与"读剪贴板"的时序（用 `AddClipboardFormatListener` 而不是轮询）。

## 3. macOS（第四端，或提前到第二）

### 能力盘点

| 能力 | API | 可靠性 |
|---|---|---|
| 辅助功能 | `AXUIElement` + `AXIsProcessTrusted` | 中高（可在设置里授予） |
| 剪贴板 + 全局热键 | `NSEvent.addGlobalMonitorForEvents` / `MASShortcut` | 高 |
| 服务菜单 | NSServices | 高（选中文本 → 右键 → 服务） |
| 输入法 | InputMethodKit | 重（同 iOS 的拼音问题） |

### 推荐路径：同 Windows（热键 + 剪贴板），再加 AX 增强

macOS 的 `AXUIElement` 比 Windows UIA 好用得多，可以真正读到 WhatsApp 窗口里的消息列表——这意味着**在 mac 上可以做到"自动识别对方语言"真正自动化**（iOS 做不到）。

但注意：macOS 的 WhatsApp 已迁移到 Catalyst 版本，AX 树在某些版本里只暴露整块文本，粒度为"整屏消息拼在一起"，做语言检测够用，做"这条是谁发的"不够用。

### 卡点

- 每次系统升级都要重新授予辅助功能权限（签名变化时会被重置）；
- 沙盒（App Store）下 AX 受限，自用不沙盒没有这个问题；
- 全局热键在沙盒下需要 `NSEvent` 全局监听 + 辅助功能授权。

## 4. 被放弃的路径：浏览器扩展（值得单独说明）

`web.whatsapp.com` 是唯一能"真正长在 WhatsApp 里"的地方：可以直接读 DOM 里的每条消息、直接改输入框，甚至做逐条内联翻译（原文下面加一行中文）。**一套 Manifest V3 扩展同时覆盖 mac / win / linux**，是投入产出比最高的形态。

**为什么没选它做首发**：你的主力场景是手机（D-13 选择了 iOS 首发）。但这不代表它不值得做——

**建议**：如果 iOS 的"三步切键盘"体验让你受不了，就立刻补一个浏览器扩展。它的实现量大概是 iOS 的 1/4，而且能同时解决 mac 和 windows 两端 60% 的需求。届时它和桌面原生端是竞争关系，不必都做。

具体做法：
- content script 注入 `[data-testid="conversation-panel-messages"]`，监听 `MutationObserver`；
- 发件框是 `div[contenteditable="true"]`，`document.execCommand('insertText')` 或直接改 `innerText` + 派发 input 事件；
- 语言检测直接复用 `LanguageDetector` 的移植版（TS）。

---

## 5. 优先级建议

| 顺序 | 平台 | 理由 |
|---|---|---|
| 1 | iOS | 已开工；能力最受限，先用它定死核心逻辑 |
| 2 | macOS | 与 iOS 同生态，设置/档案可共用 iCloud；AX 能力让"自动检测语言"终于成立 |
| 3 | 浏览器扩展 | 一次性覆盖 mac+win 的主要场景，成本最低 |
| 4 | Android | 体验最好但工程最脏（权限、保活、ROM 适配） |
| 5 | Windows 原生 | 只有在"必须脱离浏览器"时才值得做 |

> 如果目标是"尽快在真实工作里用起来"，顺序应该是：iOS → 浏览器扩展 → macOS → Android → Windows。浏览器扩展的性价比高于任何一个原生桌面端。
