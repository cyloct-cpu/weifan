# 三端路线图

范围已定为三端：**浏览器扩展 / Android / iOS**。macOS 原生不做（D-26）。

当前投入顺序：**扩展（已可运行）→ Android → iOS**（D-29）。

三端的能力上限差别很大，这决定了各自的产品形态，不是工程偏好问题：

| 端 | 读对方消息 | 改写输入框 | 需要切键盘 | 交付门槛 | 状态 |
|---|---|---|---|---|---|
| 浏览器扩展 | ✅ DOM 直读 | ✅ 直接改 | ❌ 不用 | 无 | ✅ 可运行（面板 + 划词/悬停/文档翻译） |
| Android | ⚠️ v0.1 未做 | ✅ `ACTION_SET_TEXT` | ❌ 不用 | JDK + Android SDK | 🚧 工程已搭建 |
| iOS | ❌ 读不到 | ⚠️ 只能改输入框 | ✅ 每次切两次 | Xcode + 真机 + 签名 | ⏸ 最后 |

## 二、Android（进行中）

### 为什么值得做，而且比 iOS 早

- **不需要切键盘**：无障碍服务可以直接读当前输入框、直接 `ACTION_SET_TEXT` 写回。用户打完中文点一下（甚至只打一个后缀）就完成，这是三端里唯一能做到"零打断"的。
- **能读对方消息**：无障碍节点树里有整个会话，语言检测真正自动化。
- **有现成实现可抄**：SwiftSlate（Kotlin / MIT / 已上 F-Droid）、JevChat-Jarvis（MIT，5000+ star）都跑通了同一条路。

### 推荐实现方案

**主路径：无障碍改写 + 后缀触发**

```
在任意输入框打完中文 → 末尾加「?译」→ 自动读整段文本 → 翻译 → 原地替换
```

比悬浮球更轻：不需要悬浮窗权限，不需要点按钮，不存在"球挡住内容"的问题。来源见 `docs/06-参考项目.md` 的 SwiftSlate。

**备路径：悬浮气泡**（用于不支持无障碍改写的 App，或用户想显式点击时）。

**收件：无障碍读取 + 通知监听**

- 无障碍读聊天列表/气泡文本 → 在气泡下方插入译文（需要自绘悬浮层，或用 `AccessibilityOverlay`）；
- `NotificationListenerService` 读通知里的消息做语言检测（成本低、权限独立）。

**明确不做**：自建输入法（`InputMethodService`）。一旦接管键盘，中文输入就得自己实现，工程量大十倍。

### 关键 API 与坑

| 项 | 说明 |
|---|---|
| `AccessibilityNodeInfo.ACTION_SET_TEXT` | 用 `Bundle` 传 `ACTION_ARGUMENT_SET_TEXT_CHARSEQUENCE`；部分自绘输入框不接受，需要回退到"剪贴板 + 模拟长按粘贴" |
| 服务保活 | MIUI / EMUI / ColorOS 会在息屏后杀无障碍服务。必须做引导页：电池优化白名单、自启动、后台弹窗、锁定后台 |
| 读节点树 | 不同 App 的节点层级差异大，需要一个"归一化"层，把节点树拍平成"消息列表 + 输入框" |
| Google Play 政策 | 无障碍 API 用于非无障碍目的可能被拒。自用侧载无影响 |
| 权限组合 | 无障碍 + 通知监听 + （可选）悬浮窗，三个都要引导用户手动开 |

### 复用点

- `extension/src/core/` 全部逻辑用 Kotlin 重写（约 600–800 行）；
- `extension/tests/selftest.mjs` 的断言集当作跨语言一致性基准，Kotlin 侧要写等价测试；
- 提示词、路由阈值、风险原因定义直接照搬。

## 三、iOS（最后）

### 为什么排最后

| 事实 | 后果 |
|---|---|
| 键盘扩展读不到别的 App 的聊天内容 | "自动识别对方语言"在 iOS 上不成立 |
| 不能读输入框以外的内容 | 收件只能靠分享扩展手动触发 |
| 要输入中文就得自研拼音输入法 | 不做，于是只能"系统键盘打完 → 切微翻 → 译 → 切回" |
| 每次发送切两次键盘 | 三端里体验最差 |
| 需要 Xcode + 真机 + 签名 | 当前开发机不具备 |

### 如果将来要做，先重新选形态

三个候选，按推荐度排序：

1. **只做分享扩展**：长按对方消息 → 分享 → 看中文。成本最低（约 1/4），体验不别扭。**放弃发件方向**（发件交给扩展或 Android）。
2. **分享扩展 + 键盘**：完整但成本高，且键盘那套要维护切键盘的引导。
3. **只做键盘**：不推荐，读不到对方消息导致了半个功能缺失。

### 现有代码怎么办

`ios/` 目录下已有一套完整实现（主 App / 键盘 / 分享扩展 / XcodeGen 工程描述），**暂时归档，不删**。等有 Xcode 且确定要做时，按上面的候选重做取舍——大概率是砍掉键盘、留分享扩展。

### 必须验证的第一件事

V-01：键盘扩展能否读到 WhatsApp 输入框里已有的文本。不成立的话键盘方案直接作废，只剩分享扩展。

| 断言集 | `extension/tests/selftest.mjs` | 33 项，新端必须全部复现 |

> **一致性原则**：任何一端改了阈值、提示词、占位符格式，其他端必须同步，否则同一个客户在不同设备上会收到风格不同的译文。断言集是这件事唯一的防线。
