# 待验证清单

按"假设不成立就要改架构"的程度排序。**V-01 和 V-02 必须在写更多功能之前验证完**，它们是整个 iOS 方案的地基。

---

## V-01（致命）键盘扩展能否读到 WhatsApp 输入框里已有的文本

**假设**：`textDocumentProxy.documentContextBeforeInput` 在 WhatsApp iOS 的输入框里会返回光标前的完整文本。

**为什么关键**：D-02 的三步流程完全建立在这条上。如果 WhatsApp 的输入框（可能是自绘的）返回 `nil` 或空串，整个键盘方案就只剩"在微翻键盘上打中文"，那需要自研拼音输入法，项目规模翻十倍。

**验证方法**：
1. 找一个最简单的键盘扩展 demo（或直接用本仓库的 `WeiFanKeyboard`），装到真机；
2. 在 WhatsApp 输入框里输入 `测试123`，不要发送；
3. 切到微翻键盘，看 `previewLabel` 是否显示出这段文字。

**判定**：显示出来 → 成立；显示"输入框是空的" → 不成立。

**不成立时的替代方案**（按优先级）：
1. 改用剪贴板：在 WhatsApp 里长按全选复制 → 切微翻 → 读剪贴板（代价：iOS 16+ 粘贴权限弹窗，但只需一次授权）；
2. 放弃键盘，全部走分享扩展 + 复制回粘；
3. 改做浏览器扩展为主形态。

**顺带要测**：Telegram / Signal / WeChat 是否同样能读到（不同 App 的输入框实现不同，WhatsApp 特殊不等于全特殊）。

## V-02（致命）WhatsApp 的语音消息能否分享给分享扩展

**假设**：长按语音消息 → 分享 → 会出现微翻，且拿到的 item 是 `public.audio`。

**为什么关键**：F-09 语音转写的前提。如果拿不到音频，语音功能就只能是"在微翻 App 里录自己的声音"，价值大打折扣。

**验证方法**：真机上长按一条语音消息，看分享面板里有没有微翻；若有，看 `loadFileRepresentation` 回调是否给出非空 URL，以及文件大小是否合理（几 KB 到几百 KB）。

**可能的结果与对策**：
| 结果 | 对策 |
|---|---|
| 分享面板无微翻 | 改 `NSExtensionActivationRule`，加 `NSExtensionActivationSupportsMovieWithMaxCount` 或放宽为 `TRUEPREDICATE`（自用无审核压力）；仍不行则放弃该路径 |
| 有微翻但拿到的是链接而非音频 | 只做"语音消息无法转写"的提示 |
| 拿到音频但需解密 | WhatsApp 的 opus 通常是明文，若加密则本项目放弃语音 |

## V-03（高）占位符是否被翻译引擎保留

**假设**：`⟦0⟧` 这类占位符经过 DeepL / Google / 大模型后仍然是可识别的形式。

**为什么关键**：术语保护（D-08 / F-06）依赖它。若引擎吞掉或改写，产品名就会被译错，且用户不知情。

**验证方法**：用固定测试串分别打三家 API：
```
原文：轻舟 Pro 的定金是 500 美元，请联系 Chan。
送检：⟦0⟧ 的 ⟦2⟧ 是 500 美元，请联系 ⟦1⟧。
```
观察返回里占位符是否还在、编号是否被保留、是否被加了空格或全角化。

**当前已做的防御**：`Glossary.restore` 用宽松正则（容忍空格、全角括号）；还原失败时保留占位符不做替换（可见的失败）。

**进一步的防御**（如果实测失败率高）：
- 改用更"像正常词"的占位符，如 `ZQXM0ZQXM`（全大写无意义串），引擎更倾向于原样保留；
- 或改用"译后替换"：先把术语译成目标语言的高置信固定译法，再在译文中反查；
- 或干脆对含术语的句子一律走大模型，并在提示词里强约束（当前提示词已写）。

## V-04（高）Keychain 能否被键盘扩展读到

**假设**：App 写入的密钥，键盘扩展能读到。

**为什么关键**：读不到就表现为"键盘一直报缺少密钥"，而 App 里一切正常——这是最难自查的一类 bug。

**验证方法**：在 App 里填入 Google key → 切到键盘 → 点译。若报 `errSecMissingEntitlement` 或"缺少密钥"，则失败。

**必要条件**：
- 两个 target 的 entitlements 都有 `keychain-access-groups` 且值相同；
- 签名时该 capability 已包含在 provisioning profile 里（免费账号可能不支持自定义 group，那就退回 `$(AppIdentifierPrefix)$(CFBundleIdentifier)` 的默认组——但那样两个 target 不在同一组，只能把密钥写进 App Group 的 UserDefaults，安全性下降）。

## V-05（中）中文口语数字写法的覆盖

**假设**：金额正则能识别真实报价里的写法。

**已知漏洞**：当前正则只认阿拉伯数字 + 货币符号/单位。"一千二"、"两百五"、"3 万"（后者能认）这类中文写法**不会触发金额拦截**。

**对策**：补一组中文数字正则（`[一二三四五六七八九十百千万零两]+` 后面跟"元/块/万/千"），或对包含"价/费/付/定金/报价/成本"等词的句子无条件拦截。

**这是"漏拦"而不是"误拦"，漏拦的代价更高，建议宁严勿宽。**

## V-06（中）键盘里如何知道"我在跟谁聊"

**现状**：iOS 键盘扩展拿不到宿主 App 的会话对象，客户档案只能点「客户」按钮手动轮换。

**影响**：D-09 的自动兜底链条在键盘路径上不成立，实际退化成"手动选人"。

**可选改法**：
1. 分享扩展里让用户顺手标一次"这条来自 Juan"，键盘据"最近标记"推断（一次会话一次标记，可接受）；
2. 键盘顶部放一个最近 3 个客户的头像条，点一下即切（比循环更直观）；
3. 放弃自动，明确告诉用户"语言请自己点芯片"（最诚实、最省事）。

## V-07（中）键盘扩展的内存与长文本边界

**假设**：在 40MB 以内能完成一次 2000 字文本的翻译。

**测法**：用 Xcode 的 Memory Gauge 观察键盘进程；输入 2000 字长文点译，看是否被杀。

**对策**：长文本阈值（默认 60 字）以上走 LLM，请求体较大但仍是几 KB 级别，风险主要在响应解析与字符串拼接。必要时对超过 1500 字的输入直接提示"太长，请分段"。

## V-09（低）分享扩展在 WhatsApp 里的实际操作路径

**假设**：长按消息 → 分享 → 微翻，是两步可达的。

**实际可能**：WhatsApp 的长按菜单里"分享"藏在二级菜单，或只支持分享给联系人而不进系统分享面板。

**对策**：若路径太深，改为主推"复制 → 打开微翻 App 自动粘贴翻译"（用 `UIPasteControl` 或读取剪贴板）。

## V-11（高，但优先级可调）Apple 系统端上翻译能否在键盘扩展里用

**假设**：`Translation` framework（iOS 17.4+）可以在键盘扩展里调用，完成短句翻译。

**为什么重要**：如果成立，短句翻译变成**免费、离线、零延迟、不出网**，D-05 的成本模型和 D-10 的隐私模型同时改善——这是目前已知收益最大的一条未验证假设。

**验证方法**：
1. 在键盘扩展里写最小 demo，调用 `TranslationSession`（注意：该 API 通常要求用户先下载语言包，首次会弹系统 UI）；
2. 观察两点：扩展里能否正常创建 session；首次下载语言包时是否因为扩展无 UI 而失败。

**可能的结果**：
| 结果 | 对策 |
|---|---|
| 完全可用 | 把"短句 + 纯文本 + 无数字"路由到系统端上翻译，云端只兜长句 |
| 仅主 App 可用、扩展不可用 | 主 App 与分享扩展用系统翻译，键盘仍走云 API |
| 语言覆盖不足（比如没有小语种） | 保留现在的 DeepL/Google 兜底，系统翻译只作为英语等主流语种的加速层 |

**顺带测**：`TranslationSession` 的延迟，以及它对"中文 → 西语"这类非英语对的覆盖。

## V-13（高）扩展在真实 WhatsApp Web 里能不能跑

**假设**：`SELECTORS` 里的选择器与当前 WhatsApp Web 的 DOM 结构一致。

**为什么关键**：这是扩展唯一的未验证假设。不成立的表现是"装好了但一条译文都不出现"。

**验证方法**：装 `dist/chrome` → 打开 web.whatsapp.com → F12 Console 里依次执行：

```js
document.querySelectorAll('#main div[role="row"]').length          // 消息行，应为 > 0
document.querySelector('#main footer div[contenteditable="true"]') // 输入框，应非 null
document.querySelector('#main header span[title]')?.title          // 会话名
```

**判定**：三个都有值 → 成立；任一为 0/null → 改 `SELECTORS` 对应项。

**兜底方案**：WhatsApp 改版后优先找 `data-testid` 稳定属性；实在找不到就退回"复制到输入框旁手动触发"的降级形态。

## V-14（中）Firefox 产物是否真的能跑

**假设**：`background.scripts` + `type: module` 在 Firefox 121+ 能正常启动并响应消息。

**测法**：
1. `about:debugging#/runtime/this-firefox` → 临时载入 `dist/firefox/manifest.json`；
2. 点「检查」看 background 控制台是否有报错；
3. 打开 WhatsApp Web，看收件是否出译文。

**已知风险**：Firefox 的 `browser.*` 是 Promise 式，若某处漏用 `EXT` 而直接用了 `chrome.*`，会表现为"设置读不出来 / 消息无响应"。已统一到 `src/shared/ext.js`，但仍是首次移植最容易出错的地方。

## V-15（低）Safari 打包能否一次通过

**前置**：必须有 Xcode。

**测法**：按 `extension/dist/safari/SAFARI-README.txt` 跑 `safari-web-extension-converter`，在 Xcode 里 Run。

**已知风险**：
- Safari 对 MV3 的 `host_permissions` 授权模型更严，可能需要 `permissions.request()` 引导；
- 未签名的扩展需要在 Safari 设置里手动允许；
- 分发需要 Apple Developer 账号。
