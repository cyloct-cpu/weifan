# 方案修订（2026-10-29）

> 本文件**覆盖** `docs/00-决策记录.md` 中与之冲突的条目。冲突时以本文件为准。
> 触发修订的三件事：① 参考项目调研（`docs/06-参考项目.md`）② 开发机没有 Xcode ③ 用户确认主力设备是 Mac、语音可后置。

## 一、三个新事实

### 事实 1：iOS 是唯一"两头都缺"的端

| 平台 | 读对方消息 | 改写输入框 | 是否需要切换键盘 |
|---|---|---|---|
| 网页扩展 | ✅ DOM 直读 | ✅ 直接改 | ❌ 不需要 |
| Android | ✅ 无障碍 | ✅ `ACTION_SET_TEXT` | ❌ 不需要 |
| macOS | ✅ AX（粒度粗） | ✅ AX 注入 | ❌ 不需要 |
| **iOS 键盘** | **❌ 完全读不到** | ⚠️ 只能改输入框 | **✅ 每次都要切两次** |

原决策 D-13 的推理是"先做能力最受限的端，把逻辑定死"。调研之后这个理由不成立了：**能力最受限 ≠ 值得先做**，它只是最贵、体验最差、且做完了在三端里唯一不能被复用。

### 事实 2：安卓与网页扩展都已有跑通的参考实现

- 安卓：SwiftSlate 用"输入后缀 `?translate:es`"原地替换，已上 F-Droid；JevChat-Jarvis 用无障碍读会话 + 只填草稿不发送，5000+ star。
- 网页：至少四个 WhatsApp Web 翻译扩展开源，DOM 选择器与注入模式全部公开。

**意味着这两个端的工作量从"探索"变成"移植"**，而 iOS 键盘依然是"探索"（V-01 未验证）。

### 事实 3：开发机没有 Xcode，但 node 齐全

| 端 | 能否在当前机器开发并试跑 | 依赖 |
|---|---|---|
| 浏览器扩展 | ✅ 能，改完刷新即可 | Chrome / Edge |
| macOS 原生 | ❌ 不能 | Xcode（编译 + 签名 + 辅助功能授权） |
| iOS | ❌ 不能 | Xcode + 真机 + 开发者账号 |
| Android | ⚠️ 未确认 | Android Studio / JDK |

**这一条是决定性的**：主战场是 Mac，而唯一能在 Mac 上"今天写完今天用"的形态，是浏览器扩展。

| 原决策 | 原结论 | 新结论 | 理由 |
|---|---|---|---|
| **D-02** iOS 三步切键盘 | 核心交互方案 | **降级为备用端**，不再是主形态 | 每次发送要切两次键盘，是全方案最大的体验妥协；而扩展/安卓都不需要 |

## 三、新决策

### D-17 主形态：WhatsApp Web 浏览器扩展（MV3）

**结论**：第一版就是 Chrome/Edge 扩展，加载 `web.whatsapp.com`。

**为什么**：
- 唯一能**逐条内联**显示中文的形态（原文下面直接跟一行译文），这是 iOS 键盘永远做不到的；
- 一套代码同时覆盖 Mac 和 Windows（用户四端诉求里的一半，成本 1/4）；
- 不需要签名、不需要开发者账号、不需要审核，加载即用；
- DOM 选择器有四个现成项目可抄。

**代价**：
- 依赖 `web.whatsapp.com` 在线，且手机必须保持联网（WhatsApp 的多设备机制）；
- WhatsApp 改版会打断选择器，需要维护（这是长期成本，必须接受）；
- MV3 里 content script 受 CORS 限制，所有 API 调用要走 background service worker。

**止损点**：如果维护选择器的频率高于每月一次，就转做 macOS 原生。

### D-18 交互：收件自动内联，发件一键替换

**收件**（对方消息）：
- 默认**自动**在原文下方插入中文译文（灰色小字，带"译"标识）；
- 用 `IntersectionObserver` 只翻译进入视口的消息，滚动到哪译到哪；
- 已翻译的消息用 `data-wf-done` 标记，避免重复请求；
- 单条超过 1500 字不自动译，显示"点此翻译"。

**发件**（输入框）：
- 输入框右下角浮动「译」按钮，`Ctrl+Enter` 等效；
- 点一下 → 替换输入框内容为译文（`execCommand('insertText')`），**不自动发送**；
- 命中金额 → 先弹确认条，再点一次才替换；
- 替换后 8 秒内显示「撤销」，可换回中文。

**为什么不做"边打边译"**：每个停顿一次请求，费用与延迟双爆。只在点击时请求——这条与 D-04 一致。

### D-19 语言策略：会话级检测 + 手动锁定

**结论**：
1. 进入会话时，取最近 10 条对方消息做一次检测，结果记在会话上；
2. 之后每条新消息单独检测，若与记忆冲突且置信度高，更新记忆并**在工具栏提示"对方似乎改用西语"**；
3. 顶部小工具栏始终显示当前目标语言，点一下可锁定/切换（锁定后不再自动改）；
4. 检测不出来 → 客户档案 → 兜底英语。

**这比 iOS 版强的地方**：iOS 根本没有"最近 10 条对方消息"，只能靠猜和手动；扩展可以直接读。

### D-20 内核：TypeScript（零构建，ESM）

**结论**：`extension/src/core/` 用**原生 ES module + JSDoc 类型注解**写，不引入打包器。

**为什么不用 TS + 构建**：
- 自用场景下"改一行刷新就生效"比类型检查更值钱；
- 免掉 node_modules、免掉构建产物与源码不同步的问题；
- JSDoc 已经能在 VS Code 里给出完整的类型提示，收益的 80% 拿到了。

**为什么不用 WXT / Plasmo 这类框架**：它们是给"要上架、要跨浏览器、要热更新"的项目准备的。我们这个只有 3 个页面 + 1 个 content script，框架带来的抽象成本大于收益。**如果将来上架，再迁 WXT**。

**与 Swift 版的关系**：Swift 的 `WeiFanCore` 保留，作为**行为规格**。两边的断言集必须一致（`core/Scripts/main.swift` ↔ `extension/tests/selftest.mjs`）。改一边必须改另一边——这是四端一致性的唯一保障。

### D-21 服务商：新增 Groq 作为大模型首选，保留 DeepSeek

**结论**：大模型通道默认 Groq（Llama 3.3 70B），可切 DeepSeek / OpenAI 兼容端点。

**为什么**：Transify 的实测数据是"Groq 上 Llama 3.3 70B 通常 <200ms"。如果属实，**长句也能走大模型而不牺牲手感**，这会直接改变混合路由的阈值（可以把"含数字就走大模型"之外的分界线进一步放开）。

**待验证**：这个 <200ms 是首 token 还是完整响应，必须自己测（新增 V-13）。

### D-22 密钥存储：`chrome.storage.local`，明确告知风险

**结论**：密钥存 `chrome.storage.local`（仅扩展可读，页面脚本读不到），不加密。

**为什么**：chrome.storage 已经是同源隔离的，加密的密钥最终也要在本扩展里解密，收益接近于零。真正的风险是"别人拿到你的电脑"——这靠系统锁屏解决，不靠应用层加密。

**必须做的**：设置页明确写一句"密钥以明文保存在本机浏览器配置里"，不装作安全。

### D-23 语音：后置，但保留接口

**结论**：v1 不做语音。`core` 里保留 `transcribe()` 的空实现与调用点，等语音变成刚需再接 Whisper 或 whisper.cpp。

**代价**：对方发语音时只能看到"[语音消息]"，需要自己点开听。

### D-24 macOS 原生：第二阶段，且只在扩展不够用时做

**结论**：扩展稳定运行一个月后，再评估是否做 macOS 原生 App。

**做它的唯一理由**：能通过 AX 读窗口，实现"全局任意 App 都能译"（而不只 WhatsApp Web），以及不依赖浏览器在线。

**不做它的理由**：需要 Xcode（当前机器没有）、需要辅助功能授权、WhatsApp Catalyst 的 AX 树粒度粗（可能只给整块文本）。

### D-25 iOS：降级为最末位，且形态待定

**结论**：iOS 从"首发"改为"最末位"。真要做时，先重新评估形态：
- 键盘扩展（原方案，三步）；
- 或干脆只做分享扩展（长按消息 → 分享 → 看译文），成本更低、体验更顺（不用切键盘），**放弃发件方向**，发件仍在 Mac 上做。

**这是原方案里最需要被推翻的一处**：为了在手机上"打中文发西语"，要付出切两次键盘的代价，而这个需求在 Mac 主战场的场景里根本不高频。

# 第二轮修订（同日）：确认为三端，取消 macOS 原生

用户在看完调研后明确了范围：**只做三个端——iOS、Android、浏览器扩展（覆盖 Windows 与 Mac 上的主流浏览器），macOS 原生不做。**

## 新决策

### D-26 macOS 原生：取消（原 D-24 作废）

**结论**：不做 macOS 原生 App。

**为什么**：macOS 原生唯一的独有能力是"通过 AX 读任意 App 的窗口"，而 WhatsApp 在 Mac 上真正被日常使用的入口就是浏览器（web.whatsapp.com）或桌面客户端。**浏览器扩展已经能覆盖同样的会话，且不用编译、不用签名、不用辅助功能授权**。为了一点 AX 能力维护一套 Swift 工程不划算。

**代价**：无法翻译桌面客户端（WhatsApp Desktop）里的对话；无法做到"任意 App 都能译"。

**如果将来后悔**：先看 `docs/03-三端路线图.md` 里保留的 AX 方案要点，再决定。

### D-27 浏览器覆盖：一份源码，三份产物

**结论**：源码只有一份 `extension/src/`，用 `node scripts/build.mjs` 生成三个产物：

| 产物 | 覆盖浏览器 | 后台模型 | 能否本机验证 |
|---|---|---|---|
| `dist/chrome` | Chrome、Edge、Brave、Opera、Vivaldi（全部 Chromium 系） | MV3 service worker | ✅ 能（本机有 Chrome） |
| `dist/firefox` | Firefox 121+ | MV3 **事件页**（`background.scripts`） | ⚠️ 本机未装 Firefox |
| `dist/safari` | Safari 16.4+（macOS） | MV3 service worker | ❌ 需 Xcode 包装 |

**为什么不能"一个 manifest 通吃"**：
- Chrome 只认 `background.service_worker`；
- Firefox 的 MV3 后台是事件页，必须用 `background.scripts`，且必须有 `browser_specific_settings.gecko.id`（没有它会拒绝签名/安装）；
- 两者对彼此的键互为忽略，但 Firefox 120 之前的版本会因 `service_worker` 存在而完全不启动后台——所以**分开打包比"两个键都写"更稳**。

**代码层的兼容点**（已实现，见 `src/shared/ext.js`）：
- Firefox 的 `browser.*` 是 Promise 式，Chromium 的 `chrome.*` 是回调式；
- **`await chrome.storage.local.get(...)` 在 Firefox 里会得到 `undefined`**，这是移植时最常见的静默失败；
- 统一入口：模块上下文用 `EXT`/`sendToBackground`，content script 内联等价实现（content script 不能用 import）。

### D-28 Safari：代码已就绪，交付被 Xcode 阻塞

**结论**：`dist/safari` 会正常生成，但要装进 Safari 必须：

```bash
xcrun safari-web-extension-converter ./dist/safari \
  --project-location ./safari-project --app-name "微翻" \
  --bundle-identifier com.weifan.safari
```

然后在 Xcode 里选 Team、Run 一次，再到 Safari 设置 → 扩展里勾选。

**当前状态**：开发机没有 Xcode，**这一步做不了**。装 Xcode 之后大约 30 分钟能通。

**要不要为此装 Xcode**：如果 Safari 是你 Mac 上的主力浏览器，值得；如果主力是 Chrome/Edge，可以一直不做。

### D-29 三端顺序：扩展（进行中）→ Android → iOS

**结论**：三端里扩展已可运行；下一个投入 Android，iOS 最后。

**为什么 Android 在 iOS 之前**：
- Android 用无障碍服务 + `ACTION_SET_TEXT` 可以**不切键盘**直接改写输入框，交互上比 iOS 高一个量级；
- SwiftSlate / JevChat-Jarvis 已经把这条路跑通并开源，属于移植而非探索；
- iOS 即使做出来，也是"切两次键盘 + 读不到对方消息"的最差体验，且它需要的 Xcode 同样缺失。

**三端的能力差异（决定了各自的上限）**：

| 端 | 读对方消息 | 改写输入框 | 需要切键盘 | 交付门槛 |
|---|---|---|---|---|
| 浏览器扩展 | ✅ | ✅ | ❌ | 无（已可运行） |
| Android | ✅ 无障碍 | ✅ `ACTION_SET_TEXT` | ❌ | Android Studio / JDK |
| iOS | ❌ | ⚠️ 仅输入框 | ✅ 每次两次 | Xcode + 真机 + 签名 |

## 本轮遗留的现实约束

| 缺口 | 影响 | 补上需要 |
|---|---|---|
| 没有 Xcode | iOS 全端 + Safari 打包 无法交付 | 安装 Xcode（约 10GB） |
| 没有 JDK / Android SDK | Android 端无法编译验证 | 安装 Android Studio 或 JDK + cmdline-tools |
| 没装 Firefox | Firefox 产物未实测 | 装 Firefox，`about:debugging` 临时载入 |
| 未在真实会话验证 DOM 选择器 | 扩展可能一装上就不出译文 | 打开 WhatsApp Web 试一次 |

# 第三轮：Android 端落地（同日）

## D-30 Android 交互用「后缀触发」，不用悬浮球

**结论**：在任意输入框打完中文，末尾加 `?译`，服务自动读整段、翻译、原地替换。触发词可配置。

**为什么推翻原计划的悬浮球**：调研发现 SwiftSlate 已经用这个交互跑通并上了 F-Droid。它比悬浮球好在：
- 不需要悬浮窗权限（少一个用户要理解的东西）；
- 不遮挡内容；
- 触发点就在文字里，用户不需要"想起来去点某个球"。

**代价**：多打两个字符；触发词与正常文本冲突的概率虽低但不是零（可改）。

## D-31 风险拦截在 Android 上退化为"复制而非替换"

**结论**：命中硬风险（默认含金额）时**不替换输入框**，改为把译文写进剪贴板并提示。

**为什么**：无障碍服务里没有合适的轻量 UI 来做确认条；弹 Activity 会打断用户当前操作。复制是把决定权交回用户的最短路径。

**后续**：用 `TYPE_ACCESSIBILITY_OVERLAY` 做一个不抢焦点的确认条，替换掉这个退化方案。

## D-32 Android 零第三方依赖

**结论**：不引 AndroidX / OkHttp / Gson / Compose。UI 用纯 framework 视图，JSON 用系统自带 `org.json`，网络用 `HttpURLConnection`。

**为什么**：
- 设置页就一个表单，不值得为它引整套 UI 框架；
- 依赖为零 → APK 小、编译快、不会因某个库抬升 minSdk 而卡住；
- 排查问题时少一层抽象。

**代价**：UI 代码比 Compose 啰嗦；Kotlin 侧暂时无法在 JVM 上跑单元测试（`org.json` 是 Android 才有的），33 项断言集需要 Robolectric 或 instrumented test 才能复现。

# 第四轮：扩展弹窗化 + 六家大厂免费额度（同日）

## D-33 扩展改成"点图标弹面板"，不再直接跳设置页

**结论**：点图标弹出 360px 面板（语言 / 模式 / 服务 / 主按钮 / 四格功能 / 底栏），设置页只放密钥与参数表单。

**为什么**：面板是天天用的，设置页是配一次的。混在一起两边都难用——面板塞不下密钥表单，设置页塞不下每天要点的按钮。

**代价**：面板装不下六家的密钥表单（百度要 appid+secret、腾讯要 SecretId+SecretKey、阿里火山要 AK/SK），必须分两层。

## D-34 免费额度走"用户自取 key"，不代理、不内置

**结论**：百度 / 腾讯云 / Google / DeepL / 火山引擎 / 阿里云，密钥由用户自己在平台申请，填进设置页；扩展只做路由与降级。

**为什么**：
- 代理要养服务器、要防刷，密钥一旦从客户端泄露就会被平台封号，全盘皆输；
- 用户自取 → 零运维、零合规风险，额度用完也是用户自己的事；
- 与 D-35（暂不做付费层）方向一致。

**代价**：新用户装完要去平台注册一次，这是唯一的一次性成本。

## D-35 暂不做付费层

**结论**：不做账号、不做订阅、不做 License 校验。"免费额度 / 自定义 API"只是两个功能分组，不是两个付费档。

**为什么**：现在还没有用户，先把能力做全。收费是商务问题，不是技术问题。

**后续**：真要收费，"自定义 API"那一组加锁就是最自然的收费点。

## D-36 两种模式用分段开关 + 服务下拉

**结论**：面板顶部「免费额度 / 自定义 API」两段切换，下面一个服务下拉；免费额度组第一项是"自动（按语种优选）"。

**为什么**：截图那种单一"翻译服务"下拉装不下模式概念。分段开关让模式一眼可见，将来收费直接在这把自定义那侧锁上。

## D-37 主按钮只做"选区 / 剪贴板"，不做整页翻译

**结论**：点一下翻当前页选区，没选区就翻剪贴板，结果显示在面板里。整页翻译（DOM 遍历器）不做。

**为什么**：整页翻译要写 DOM 遍历器，而且会和 WhatsApp 收件自动翻译互相改 DOM（两边都替换节点）。选区/剪贴板用 10% 的工拿到 80% 的体验。

## D-38 划词与悬停共用一套气泡：划词可操作，悬停只读

**结论**：划词气泡 = 可编辑译文 + 复制 + 一键替换原文；悬停气泡 = 只读译文，0.6 秒节流，同一个词不重复请求。

**为什么**：划词是"我要用"，悬停是"我瞄一眼"，操作深度天然不同。悬停若做成可编辑，鼠标扫过页面会疯狂发请求。

## D-39 文档翻译：本地解析，不上传

**结论**：txt/md/csv 直读；PDF 用内置 pdf.js 抽文字；docx 解 zip 读 `word/document.xml`，逐段翻译后写回新 docx（段落结构与数量保留，字体/表格不保留）。

**为什么**：贸易场景的单据、发票、规格书基本是 PDF；把文件传到第三方服务器等于把客户报价单交出去。

**代价**：Word 排版保不住，PDF 版式保不住（只给纯文本）；扩展体积 +1.7MB（pdf.js + worker）。

## D-40 页面代理用 manifest 注入全站，权限换体验

**结论**：`content_scripts` 匹配 `<all_urls>`，划词/悬停在任何页面都能用；不依赖"先点一次扩展图标"的 activeTab 临时授权。

**为什么**：activeTab 方案每次刷新页面就失效，划词体验会断。

**代价**：安装时 Chrome 会提示"读取和更改您在所有网站上的所有数据"——这是这类工具的常规代价，靠面板里的两个开关让用户随时能关。

## D-41 每日额度保护（防平台超量计费）

**结论**：设置页可给单个服务商设"每日字符上限"（默认 0 = 不限）。达到上限当天不再用这家，自动降级到下一家。

**为什么**：免费额度是有上限的，用户自己的 Google key 若绑了信用卡，超量是**真扣钱**的。扩展侧主动设闸，比事后被发现账单好。

## D-42 本轮只改扩展，Android 端服务商层暂不同步

**结论**：Android 仍是原来的四家（Google / DeepL / Groq / OpenAI 兼容），本轮新增的六家与自定义 API 多档案只在扩展侧实现。

**为什么**：本轮需求全部围绕扩展弹窗；Android 的设置页与交互是另一套设计，硬同步会把两边都做成半成品。

**后果**：JS 与 Kotlin 的服务商层暂时不一致。Swift 版（`core/`）的 providers 已被 JS 版取代，**仅作规格存档**（macOS 原生已在 D-26 取消，且本机 Swift 工具链不可用，无法编译验证）。

## D-43 服务商扩到八家，补 Azure 微软翻译与 Yandex Translate

**结论**：在原有六家之外新增 **Azure 微软翻译** 与 **Yandex Translate**，并把显示名统一成官方产品名：

| # | 服务商 | 鉴权 | 免费额度 |
|---|---|---|---|
| 1 | 百度翻译开放平台 | MD5(appid+secret) | 通用版 5 万/月（高级版 100 万）；大模型版另计 |

| 3 | Google Cloud Translation | API Key | 每月 50 万字符 |
| 4 | DeepL API Free | API Key | 每月 50 万字符（key 以 :fx 结尾） |

**为什么是这两个**：

**Azure 的坑**：请求体是**数组** `[{"text": ...}]`，不是对象；区域资源要带 `Ocp-Apim-Subscription-Region` 头（做成选填）。

## D-51 Android 端补齐四大功能（划词 / 文本 / 文档）

**结论**：Android 端不再只有"输入框触发词"，补上浏览器那套翻译能力。

**先说清一件事**：**「鼠标悬停」在手机上不存在**（没有鼠标指针）。Android 上对应的是**划词**——
在任意 app 里选中文字，系统菜单里出现「微翻」。所以 Android 端做的是：

| 扩展 | Android | 做法 |
|---|---|---|
| 划词翻译 | ✅ 划词翻译 | `ACTION_PROCESS_TEXT` intent-filter，任何 app 选中文字都能调起 |
| 文本翻译 | ✅ 翻译页 | 独立 Activity，粘贴任意文本 |
| 文档翻译 | ✅ 文档翻译 | 文件选择 → 逐段翻译 → 存回文件 |
| 鼠标悬停 | ❌ | 手机没有鼠标，改用划词 + 输入框选词 |

**划词的官方约定**（照文档实现，不是猜的）：
- 输入：`EXTRA_PROCESS_TEXT`（选中的文字）、`EXTRA_PROCESS_TEXT_READONLY`（原文能不能被替换）；
- 输出：`setResult(RESULT_OK)` + 结果里再放一份 `EXTRA_PROCESS_TEXT` → 系统自动替换原文；
- 系统用 `startActivityForResult` 启动我们，所以**页面已开着时第二次划词走 onNewIntent**，两种入口都要处理。

**方向自动判断**：划词时先检测源语言 —— 中文 → 翻成兜底目标语言；外文 → 翻成简体中文。
不判断的话，选中一段英文、目标也是英语，译文会原样返回，看着像没翻译。

**文档翻译支持 txt / md / csv / docx**：
- 文本类按空行切段；
- docx 是 zip + `word/document.xml`，用**纯 JDK**（java.util.zip + javax.xml）读写，
  保留段落结构与数量，字体/表格/分栏不保留 —— 与扩展侧 `src/doc/doc.js` 同一套算法。

⚠️ **PDF 暂不支持**：Android 上抽 PDF 文字得把 pdf.js 塞进 WebView，还要解决 worker 的加载域名问题，
不适合硬塞。扩展侧已支持 PDF。

**新增文件**：`TranslateActivity.kt`、`TranslateDocActivity.kt`、`core/Docx.kt`、`Ui.kt`、`Brand.kt`（色板抽成共享）。


## D-52 语言框可输入 + 原文译文一键对调 + 同时翻译两种语言

**用户诉求**（三条一起）：目标语言不能只能选、要能输入；原文和译文要能一键对调；再加一个语言框，
一次能翻两种语言，三种语言之间能快捷切换。

**结论**：翻译页（扩展文本翻译页 + Android 翻译页）统一改成**三个可输入的语言框**：

```
[源语言      ] ⇄ [目标语言     ] ⇄ [第二个目标（选填）]
原文框                              译文框
                                     译文框2（填了第二个目标才出现）
```

- **可输入**：Android 用 `AutoCompleteTextView` + 自定义 Filter（名称或代码**包含**输入内容即命中，
  输入 "en" 命中「英语（en）」、输入 "英语" 也命中）；扩展用原生 `<input list>` + `<datalist>`，零依赖。
- **第一个「⇄」**：源语言 ⇄ 目标语言互换，**语言和原文/译文内容一起换** —— 原文是中文译文是英文，
  按一下就变成原文英文、译文中文，不用重新翻译。
- **第二个「⇄」**：两个目标语言互换，两份译文对调。
- **同时两种语言**：填了第二个目标语言，一次翻译输出两份译文（两个目标并发请求）。

**顺带加了一条"同语言自动翻向"**：源与目标同语言 = 白翻一遍（英→英译文原样返回，看着像没翻），
现在自动翻到另一边并在状态里说明「源与目标同语言，已自动改为 简体中文」。

**失焦还原**：语言框里打了字但没匹配到任何语言时，失焦自动还原成当前语言的规范写法，不留乱码。


## D-53 翻译页重排：语言选择放中间，每个译文框自带复制

**用户标注截图后的要求**：语言选择放在中间；加一个译文框；只有原文能输入；
输入原文时可以同时翻译成另一种语言，但**不是强制的**（清空第三种语言就不翻）；
每个译文框都要有复制按钮。

**结论**：翻译页（扩展文本翻译页 + Android 翻译页）统一改成：

```
原文框（唯一可输入）
[翻译]
语言   [源语言 ] ⇄ [目标语言] ⇄ [第二个目标（选填）]
译文                    [复制]
译文（第二个目标语言）    [复制]
```

- **语言行挪到中间**：夹在原文与译文之间 —— 语言描述的是"输出成什么"，所以放在输入和输出之间。
- **只有原文能输入**：译文框一律只读（Android 用 TextView，扩展用 readonly textarea）。
- **第二个译文框常驻**：不再因为没填第三个语言就隐藏，只显示一句提示；
  **清空了第三个语言 → 不再翻它**（目标列表为空就不发那个请求），属于"可选"而非"强制"。
- **每个译文框自带复制按钮**：不用再翻到底部找"复制译文"。

**没有做"边打字边翻译"**：那会每敲几个字就发一次请求，把免费额度烧光。
触发点仍然是「翻译」按钮（划词入口除外，那个是自动的）。


## D-54 三档昼夜切换（昼 / 夜 / 跟随系统 + 自定义时段）

**用户诉求**：增加昼夜切换，一共 3 种模式 —— ①昼 ②夜（暗色调）③跟随手机系统，并且**可以自行设置时间改变昼夜**。

**结论**：两端都做，同规格。

### 判定逻辑（扩展 JS 与 Android Kotlin 两份实现，算法完全一致）

```
mode = 昼        → 恒为浅色（哪怕系统是暗色）
mode = 夜        → 恒为暗色（哪怕系统是浅色）
mode = 跟随系统  → 启用自定义时段 ? 按时刻判定 : 跟系统
```

自定义时段**跨零点也算**（22:00 – 07:00 这种），区间是「起点闭、终点开」。

### 为什么不用纯 CSS 的 prefers-color-scheme

手动指定夜间时，它会跟系统打架（用户选了"昼"，系统是暗色，CSS 媒体查询仍会判暗）。
所以改成 **JS/Kotlin 算出最终是昼是夜，写到 `<html data-theme="dark">` 上**，样式表只认这个属性。
扩展侧的 `@media (prefers-color-scheme: dark)` 全部改成 `:root[data-theme='dark']`。

### 扩展侧

- 新增 `src/shared/theme.js`：判定 + 应用 + 监听（系统主题变了、时段跨界了自动重算）；
- 设置页加「外观 · 昼夜切换」分组：三档分段 + 自定义时段开关 + 起止时间输入；
- 弹窗顶栏加一个**三档循环的小按钮**（太阳 / 月亮 / 半圆三个图标），点一下就切；
- 四个页面（弹窗 / 设置 / 文本 / 文档）都在 `<head>` 放一段**内联脚本同步读 localStorage 镜像**——
  模块脚本是延迟执行的，等它跑到时页面已经画过一次，会有闪白；
- 文本页与文档页跟随全局设置（它们本来就是独立页面，之前各自一套）。

### Android 侧

- 新增 `core/Theme.kt`：与扩展同算法；
- 新增 `BaseActivity.kt`：所有页面继承它。
  **不用 AppCompatDelegate.setDefaultNightMode**（刻意零依赖，不引 AndroidX），
  改用框架自带的 `applyOverrideConfiguration` 改 uiMode —— 这样连系统对话框也跟着变暗；
- `Brand.kt` 拆成 `LIGHT` / `DARK` 两套色板，由上层判定传哪一套；
- 设置页加同样的「外观」分组，改主题**立即生效**（不用点保存）；
- 每 30 秒检查一次，夜间时段跨界时自动重建界面。

### 踩的坑

1. **`switchRow` 返回的 Switch 已经有父容器了**，再 `addView` 就崩
   （`IllegalStateException: The specified child already has a parent`）。
   我照着别处的写法多写了一次 `addView` —— 编译期发现不了，运行即崩。
2. **竖向 LinearLayout 里 `width=0` + `weight=1` 会让宽度真的变成 0**
   （weight 在竖向布局里分配的是高度，不是宽度）。时间输入框因此完全看不见。
3. **主题切换会 recreate 整个页面，滚动位置丢失** → 用 `onSaveInstanceState` 存 scrollY 再恢复。
4. **「跟随系统」时改主题不需要 recreate**（配色不是被主题决定的，是被系统决定的），
   白白重建会让页面弹回顶部。改成只在深浅真的变了时才重建。
5. CSS 的 `mask` 图标要**纯 fill 路径**才可靠 —— 用 `stroke` + `fill="none"` 时，
   auto 那个半圆渲染成了实心圆。三个图标最终都改成纯 fill 的 path。


## D-55 竞品对照后的本轮优化方向（P0：右键菜单 / 快捷键 / TTS）

**背景**：对照沉浸式翻译、划词翻译（hcfy）、DeepL 扩展与若干 WhatsApp 专用翻译扩展做了
一轮功能盘点（对照矩阵与来源见 `docs/08-竞品对照与优化清单-2026-10-30.md`）。
微翻的核心闭环（收件双语 + 发件改写 + 九家降级 + 额度保护）在同类里已属第一梯队，
**差距集中在触发方式的多样性与译后体验**，不在翻译能力本身。

**结论（本轮做 P0，落地步骤见 `docs/09-开发计划-2026-10-30.md`）**：

1. **右键菜单「用微翻翻译」**——三大竞品全有而微翻没有的最基础触发方式；
   走与划词气泡同一条链路，不新增第二套展示。
2. **键盘快捷键 ×3**（翻选区 / 悬停开关 / 打开文本页）——补齐"不碰鼠标"的最后一环；
   默认键位用 Alt+Shift 系（扩展惯例，避开系统占用），用户可自改。
3. **译文朗读 TTS（两端）**——用浏览器 / 系统内置语音合成，**零网络请求零费用**，
   与"额度保护"哲学一致；语言映射是纯函数，两端同规格并进断言集。
4. **先收尾工作区遗留的「设置页分组折叠」**，再开新活。

**明确不做**：输入框边写边译（烧额度，D-53 已定）、视频字幕 / 图片 / EPUB（场景外）、
整页双语对照（WhatsApp 是消息流，消息级双语已覆盖）。

**平台差异的处理**：Android 没有右键与全局快捷键——对应物是已有的系统划词菜单与主页入口，
记录差异（见 09 的差异表）而不是硬造入口；TTS 两端都做，触发点与映射同规格。

**P1 下一轮**：上下文连续翻译（默认关 + 隐私开关）→ 常用语 / 翻译历史 → 备选译文 → 气泡固定 → 缓存持久化。


## D-55 设置页分组改成可折叠

**用户诉求**：设置页的分组（发件 / 额度保护 / 外观…）一直挂着太占空间，要能收起来。

**结论**：**点分组标题就展开/收起**，两端同规格。默认只展开最该看见的那一组。

| 分组 | 默认 | 说明 |
|---|---|---|
| 翻译服务 | **展开** | 最核心，一进来就该看见（模式 + 服务下拉 + 九家胶囊） |
| 发件 / 收件 / 额度保护 / 外观 / 术语 | 收起 | 需要时点标题展开 |
| 翻译工具（仅 Android） | 展开 | 只有两个入口按钮，占地方小 |

**折叠时保留标题与说明文字** —— 说明是"这个分组是干什么的"，收起来也能看到语境。
收起状态只隐藏分组内容，不隐藏标题行。

**交互细节**：
- 右上角一个 ▾ 箭头，展开朝下、收起朝上（旋转 180°）；
- 标题行是 `role="button"` + `tabindex="0"`，**回车 / 空格也能切换**（键盘可达）；
- 展开时有 0.18s 的淡入下滑动画。

**实现差异（两端）**：
- 扩展：纯 CSS（`.is-collapsed` 隐藏子元素）+ JS 绑定点击，`::after` 画箭头；

### D-56 修订（同日，用户给了设计方向）

**用户改法**：不做独立的"优先级编辑器"，**胶囊网格本身就是编辑器**——
每个渠道（九家 + 自定义接口）的胶囊上直接放**启用开关**，胶囊支持**拖动排序**，
**视觉顺序（左→右、上→下）即降级链**；自定义接口支持添加多个（Android 目前只支持一个，是缺口）。

随此修订：
- **模式单选（免费额度 / 自定义 API）整体取消**——统一网格后它没有存在意义；
  网格 = 全部渠道混排，服务下拉列出全部已配置服务（跨组）。
- 运行时不再按 mode 过滤链路；`settings.mode` 字段废弃（旧存量忽略）。
- 存储：`settings.chainOrder`（全量视觉顺序）+ `settings.chainOff`（停用的 id）；
  Android 端两条逗号连接的 SharedPreferences 字段 + 自定义接口改 JSON 数组（旧单条字段自动迁移）。
- 服务下拉三档语义不变：自动 / 按我的排序（selection = 'priority'）/ 只用某一家（不降级）。
- 拖动实现：扩展用原生 HTML5 drag & drop（零依赖）；Android 用 long-press + View.startDragAndDrop。

### D-54 修订（同日）：昼夜切换放到右上角图标

**用户诉求**：外观不需要单独展开一个分组来配——**右上角直接放一个昼夜图标，点一下就切**。

**结论**：
- 设置页 / 文本页 / 文档页的**顶栏右上角**（徽标旁）都加了昼夜图标，点一下在 昼 → 夜 → 跟随系统 → 昼 循环，立即生效并存盘（与弹窗顶栏的小按钮同款，样式上移到 `shared/theme.css` 四页共用）。
- 设置页「外观」分组**瘦身**：撤掉三档单选（图标取代它），**保留「自定义夜间时段」**——时段是图标表达不了的配置，只在「跟随系统」档生效。
- Android 主页品牌行右上角加了同款循环图标（☀ / ☾ / ◐），外观分组保留（三档单选 + 时段）。
- 循环顺序收敛为纯函数：扩展 `shared/theme.js#nextThemeMode` ↔ Android `Theme.nextMode`，同规格进断言集。
